# UI Rewrite Handover

Released as v0.93.2 and merged: `main` and `feat/ui-rewrite-foundation` both
point at the release commit.

Read the "Traps" section before touching any stylesheet. Most of the bugs in
this project were invisible — no error, no failing test, no log line — and
several were caused by fixing the previous one.

---

## Where things stand

110 of 114 templates are styled by Tailwind + daisyUI. The four excluded are
the email and PDF exporters, which emit standalone documents with their own
inline styling and never load the app stylesheet.

`base.html` links five stylesheets, down from eight:

| file | role |
|---|---|
| `ion.css` | the single build: Tailwind + daisyUI + ION's theme + what survived `style.css` |
| `lucide.css` | icon font |
| `quill.snow.css` | editor, third-party |
| `ion-migrated-styles.css` | 25 rules, residue of the v0.31.21 inline-style migration |
| `alert-detail.css`, `ion-workspace.css`, `ai-chat.css` | page-scoped sheets, still legacy |

Retired: `ion-ui.css`, a second `tailwind.css` build, `design-system.css`, and
the `style.css` `<link>`.

### How ion.css is built

```bash
./frontend/tailwindcss.exe -i ./frontend/tailwind-daisy.input.css \
                           -o ./src/ion/web/static/css/ion.css --minify
```

No Node. The binary is **gitignored**, so a clone has none: the version is
pinned in `frontend/TAILWIND_VERSION` and `tests/test_tailwind_build_pin.py`
fails if the shipped `ion.css` was built by anything else. Building with a
different minor rewrites most of the utility layer while looking like an
ordinary diff. **Import order in `tailwind-daisy.input.css` is load-bearing**
— see Traps.

| input | what it is |
|---|---|
| `frontend/ion-legacy.css` | what survived `style.css`: 14 component rules that deliberately override daisyUI, plus the eight accent themes |
| `frontend/daisyui.trimmed.css` | daisyUI with unused responsive variants stripped, generated by `tools/trim_daisyui.py` |
| `frontend/daisyui.css` | the pristine vendored dist — never edit, it is the trim's source |
| `frontend/ion-daisy-theme.css` | maps daisyUI's slots onto ION's tokens, plus ported ION components and bridges |

## Traps

**1. Unlayered beats layered, but only per declaration.**
ION's rules are unlayered; daisyUI's are in `@layer daisyui.*`. ION wins for
every property it *declares*, and daisyUI fills the rest. This caused the
worst bug in the project: ION's `.modal` overrode `display` but said nothing
about `visibility`, so daisyUI's `visibility:hidden` applied and every opened
modal was laid out and invisible. If you override a daisyUI component, check
what else that component sets.

**2. `ion-legacy.css` must import BEFORE `tailwindcss/utilities.css`.**
Both are unlayered, so the later one wins, and Tailwind utilities have to beat
the legacy component rules — `p-4` must override `.card`'s padding. Move the
import after the utilities and that flips silently on every element carrying
both.

**3. Never boost `hidden`'s specificity.**
It is *meant* to be overridden by responsive variants. `<nav class="hidden
md:flex">` is how the navbar works, and a media query adds no specificity, so
`html body .hidden` at 0,1,2 beats `md:flex` at 0,1,0 and the nav vanishes at
every width. If a page's own `<style>` forces a display on an element also
written with `hidden`, fix the page rule: `.overlay:not(.hidden)`.
`tests/test_ui_rewrite_theme_parity.py` guards this.

**4. Page `<style>` blocks come after every `<link>`.**
So a page rule at 0,1,0 beats anything in `ion.css` at the same specificity.
This is why overlay rules could out-rank `hidden`.

**5. `data-ion-style` expressions are live code.**
The v0.31.21 migration froze runtime-built inline styles into CSS rules as
literal text (`background:' + sc.bg + '`). That is invalid CSS and silently
discarded — so the variables it names could disappear and nothing complained.
Moving such a declaration back into the markup makes it live again, and a
missing name throws. `tests/test_dynamic_style_scope.py` checks all 171
expressions against their enclosing scope.

**6. Tailwind's content scan needs `source(none)`.**
`@source` *adds* to the automatic scan rather than replacing it. Without
`source(none)` on the utilities import, Tailwind walks the whole repo and
compiles class names out of the changelog, the docs and the migration tools'
own data files.

**7. daisyUI's colour utilities do not exist in this build.**
daisyUI is imported as plain CSS, not as a Tailwind plugin, so its palette is
never registered with `@theme` and Tailwind generates none of it: `bg-primary`,
`bg-secondary`, `bg-base-100` and `text-secondary` compile to nothing. Its
*component* classes (`btn-primary`, `card`, `modal`) do work, as do ION's own
`@theme` colours (`bg-ink-900`, `text-ion-cyan`). The `.text-primary` used
244 times is ION's own rule in `ion-daisy-theme.css`, not a utility. When you
want an ION token, the explicit form is `bg-[var(--bg-secondary)]`.

**8. The Tailwind binary is gitignored, and a minor bump rewrites the sheet.**
v4.2.2 emits `calc(var(--spacing) * 0)` where v4.3.3 emits `0`, adds
`.start`/`.end`, and ships a different preflight font stack — roughly a hundred
rule changes that read as ordinary codegen drift in a diff. The pin lives in
`frontend/TAILWIND_VERSION`, guarded by `tests/test_tailwind_build_pin.py`.
A correct build reproduces the shipped `ion.css` byte for byte, modulo the
CRLF the checkout adds to the banner.

## Tools

Each is documented in its own docstring, including the bugs that shaped it.

| tool | what it does |
|---|---|
| `tools/dead_css.py` | finds unreferenced CSS. `--strict` drops a selector when ANY class in it is dead, which is correct but has a large blast radius |
| `tools/trim_daisyui.py` | regenerates `daisyui.trimmed.css`. Re-run after a daisyUI upgrade; a test asserts the committed copy matches |
| `tools/fix_dynamic_style_rules.py` | moves runtime-built declarations out of CSS into `data-ion-style` |
| `tools/ui_rewrite_audit.py --check` | per-template loss check against the baseline |
| `tools/ui_orphan_check.py`, `tools/ui_spot_check.py` | orphaned-rule and per-page checks |

**Do not run `tools/ui_rewrite_audit.py` without `--check`** — bare, it
rewrites the baseline, which is the historical reference for the whole
rewrite.

## Verification that actually works

Reading diffs does not settle cascade questions. What worked:

- **Build both stylesheets and diff computed styles in a browser.** Render
  every class the app carries, once per theme/mode, and compare ~45 computed
  properties per element. The `style.css` retirement was proved this way:
  4,080 elements × 2 themes, zero differences.
- **Reproduce the render.** For a JS failure, extract the function with its
  real scope and run it against a real payload. This found `sc` in one attempt
  after an hour of fruitless code reading.
- **Get real payloads without signing in.** The HTTP route is gated by
  middleware a `TestClient` override cannot reach, but the handler is an
  ordinary async function whose `Depends(...)` are default arguments — call it
  directly with a session and a user.

Known-good baseline: **12 failures on `main`**, same 12 on this branch. Two of
them (`test_v026_lab_history`, `test_worklog_api`) are order- or
time-dependent and flake on `main` too.

## What to do next

**1. The shadowed component rules in `frontend/ion-legacy.css` — 14 left, down
from 28.** Counted by intersecting every selector in the file against the class
names daisyUI defines. Every one that remains is a deliberate override, so this
item is now a judgement call rather than cleanup.

| class | rules | why it stays |
|---|---|---|
| `.alert` + `-success` / `-warning` | 6 | daisyUI inverts ION's subtle tint into a **solid green/amber fill with near-black text**, and drops `margin-bottom` so stacked alerts run flush |
| `.modal` | 4 | **never remove** — daisyUI's `display:grid` renders every closed dialog open |
| `.stat-value` | 3 | loses `tabular-nums`, and daisyUI's `order: 0` swaps the value and label inside `.stat-card` |
| `.tabs` | 1 | ION's pill container vs daisyUI's plain full-width row |

Resolved, for the record, so the same ground is not re-covered:

- **Deleted as equivalent:** `.card-title` (measured difference: `#fff` →
  `#e6e9ef` and a lost `-0.18px` letter-spacing), `.divider` (daisyUI's
  `::before`/`::after` already drew the line; ION's `border-top` was a second
  hairline), `.card-body` and `.card-header h2/h3` (inert), and
  `.text-success` / `.text-warning` (daisyUI's resolve to the same
  `#86f0a0` / `#f8b33a` via `ion-daisy-theme.css`).
- **Renamed, because daisyUI means something else by the name:** `.toast` →
  `.ion-toast`, `.footer` → `.ion-footer`. daisyUI's `.toast` is a
  *positioning* container, so ION's toasts were each being pinned to the same
  fixed coordinates and stacking on top of one another — three measured at
  `position:fixed; top:689px`. Renaming let them flow inside `#toast-container`
  as intended. Toasts are built from template literals in four places
  (`discover.html`, `observables.html`, `pcap.html`, `app.js`); a
  class-attribute scan does not find them.

Verify any further change against a computed-style diff rather than the source.
An earlier revision of this table called `.text-success` and `.text-warning`
live and `.card-header` a free deletion; both were wrong.

**2. Page weight.** Per page this is heavier than before: 90.6KB gzipped
against 64.6KB, for three fewer requests. `ion.css` is 591KB decoded, most of
it daisyUI. Component-level tree-shaking would help but needs a usage scan
worth trusting — a component can be applied by a script no scanner follows.
The responsive-variant trim was safe because a breakpoint prefix is always
static markup.

**3. The remaining page-scoped sheets.** `alerts-queue.css`,
`alert-detail.css`, `ion-workspace.css`, `ai-chat.css`. All live, no dead
rules left in any of them.

**4. Bare `catch` blocks that swallow exceptions.** Two were fixed. There are
more in `alerts.html`, and they will hide the next bug exactly as these did.

## Running it locally

```bash
docker compose up -d postgres ion
```

Elasticsearch (alerts) and Kibana (case comments) are separate containers from
the dev integration stack; start them and attach them to `ion_ion-net` with
aliases `elasticsearch` and `kibana`.

`docker compose up -d` **restarts an existing container rather than recreating
it from a new image**, and `.env` pins `ION_VERSION`. Both will silently run an
old build. Check what is actually running with:

```bash
docker inspect --format '{{.Config.Image}}' ion
```
