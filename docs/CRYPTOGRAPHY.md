# 1. Purpose

This Cryptographic Inventory is the **single source of truth** for every cryptographic operation ION performs. It is the doc reviewers ask for when they need to validate:

- algorithm strength against current advisories (NIST SP 800-131A; NCSC Cryptography Guidance)
- crypto-agility (can the algorithm be replaced without re-architecting?)
- supply-chain risk (which library implements each algorithm?)
- regulatory alignment (FIPS 140-2/3 where applicable)

# 2. Cryptographic operations inventory

## 2.1 Password storage

| Property | Value |
|---|---|
| Use | Local-password authentication (fallback when OIDC not enabled) |
| Algorithm | **bcrypt** |
| Library | `bcrypt` Python package |
| Work factor | **12** (configurable via `Settings.bcrypt_rounds`, minimum enforced 10) |
| Salt | Per-password, generated by library |
| Stored in | `users.password_hash` (Postgres) |
| Migration path | Argon2id supported as future option; library swap behind `auth/password.py` interface |

## 2.2 Session signing

| Property | Value |
|---|---|
| Use | Server-side session integrity |
| Algorithm | HMAC-SHA256 |
| Library | `itsdangerous` (FastAPI/Starlette session middleware) |
| Key length | 256-bit (`ION_SECRET_KEY`, required minimum 32 bytes) |
| Rotation | Per-deployment; rotate via `ION_SECRET_KEY` env var (invalidates all sessions) |

## 2.3 OIDC JWT verification

| Property | Value |
|---|---|
| Use | Verify Keycloak-issued JWTs |
| Algorithm | **RS256 only** (asymmetric RSA + SHA-256) |
| Library | `python-jose` (planned migration to `PyJWT`; see `_mod_exception_register.md` candidate EX-003 + pip-audit CVE-2024-23342 deferral) |
| Refused | **HS256** (symmetric) — explicitly refused at verification time |
| Refused | RS512 / ES256 / EdDSA — not implemented; would require maintainer enablement after security review |
| Keys | RSA 2048 minimum (3072 recommended; 4096 supported) |
| JWKS | Auto-refreshed; cached with TTL configurable via `ION_OIDC_JWKS_TTL_S` |

**Why RS256 only?** Asymmetric verification refuses any token signed with a shared secret — defends against a class of bypass where an attacker who can read the shared secret can mint tokens. RS256 requires the attacker to compromise the IdP's private key, which is a much stronger attack.

## 2.4 Workbench tamper-evident ledger

| Property | Value |
|---|---|
| Use | Tamper-evident sha256-chained ledger for AlertCase + ForensicCase Workbench events |
| Algorithm | **SHA-256** |
| Library | Python standard `hashlib` |
| Chain function | `event_hash = SHA256(prev_hash || canonical_json(payload))` |
| Canonical JSON | `json.dumps(payload, sort_keys=True, separators=(",", ":"))` |
| Verification | `/workbench-audit` walks chain in insertion order; row-granularity break detection |
| Storage | Postgres `case_evidence_ledger` + `forensic_case_ledger` tables |
| Migration path | Would migrate to SHA-3 if SHA-256 is collision-broken; ledger schema supports algorithm column for crypto-agility |

## 2.5 Webhook signing

| Property | Value |
|---|---|
| Use | Verify outbound webhook authenticity at the receiver (n8n, customer ITSM) |
| Algorithm | **HMAC-SHA256** |
| Library | Python standard `hmac` + `hashlib` |
| Key length | 256-bit per webhook destination |
| Key management | Stored in `webhook_destinations` table (encrypted at-rest column if customer policy mandates) |
| Signature header | `X-ION-Signature: sha256=<hex>` |
| Verification | `hmac.compare_digest(...)` — constant-time |
| Timestamp anti-replay | `X-ION-Timestamp` header; receiver SHOULD reject signatures older than 5 minutes |

## 2.6 API token (Personal Access Token)

| Property | Value |
|---|---|
| Use | Non-browser caller authentication (n8n, automation) |
| Format | `ion_pat_<base64url(32-byte-random)>` |
| Storage | Postgres `api_tokens.token_hash` (SHA-256 hash of plaintext; plaintext shown ONCE at creation) |
| Verification | Constant-time hash comparison |
| Rotation | Revocable; expiry configurable per token (default 90 days) |

## 2.7 Transport-layer security (TLS)

| Property | Value |
|---|---|
| Use | Browser ↔ Reverse Proxy (out-of-scope for ION's container; customer responsibility) |
| Recommended minimum | **TLS 1.2** |
| Preferred | **TLS 1.3** |
| Refused | TLS 1.0, TLS 1.1, SSL3, SSL2 (customer proxy responsibility) |
| Cipher suite policy | Modern (Mozilla SSL Configurator's "intermediate" or "modern" profile recommended) |
| HSTS | Recommended max-age 31536000 with includeSubDomains and preload |
| Certificate authority | Customer's choice; internal CA acceptable in air-gapped environments |

## 2.9 At-rest encryption

| Asset | At-rest crypto | Owner |
|---|---|---|
| Postgres data files | Customer responsibility (filesystem-level OR Postgres TDE) | Customer ops |
| Postgres backups | Customer responsibility (per backup policy) | Customer ops |
| Container image | Docker Hub TLS-in-transit; image digest integrity (`sha256:...`) | Docker Hub / Customer registry |
| Filesystem (PCAP files, evidence binaries) | Customer responsibility | Customer ops |
| Secrets (env vars at runtime) | Customer secrets-management responsibility | Customer SecOps |

ION does NOT implement application-level encryption-at-rest within Postgres (no row-level encryption beyond bcrypt + hashed tokens). This is a deliberate scoping decision: at-rest encryption is the customer infrastructure's responsibility (filesystem encryption, Postgres TDE, or volume encryption per customer choice).

## 2.10 Embedding vectors (pgvector)

| Property | Value |
|---|---|
| Use | Case similarity (`case_embeddings`); knowledge-base embeddings (`kb_document_embeddings`) |
| Generator | Ollama with `nomic-embed-text` model (or equivalent, configurable) |
| Storage | Postgres `vector(N)` column type via pgvector extension |
| Indexing | HNSW |
| Cryptographic role | None directly; embeddings are derived from content already classified at the content's level |

# 3. Random number generation

| Use | Source |
|---|---|
| Session IDs, API tokens, webhook keys | Python `secrets` module (OS CSPRNG) |
| Salt generation (bcrypt) | bcrypt library internal (OS CSPRNG) |
| Idempotency keys | Python `uuid.uuid4()` (CSPRNG-backed in cpython) |

ION never uses `random.random()` or `random.randint()` for security-relevant generation.

# 4. Constant-time comparisons

| Surface | Function used |
|---|---|
| API token hash compare | `hmac.compare_digest(...)` |
| Webhook signature verify | `hmac.compare_digest(...)` |
| OIDC JWT signature | Library-provided constant-time compare (`python-jose`) |
| bcrypt password compare | `bcrypt.checkpw(...)` (constant-time within bcrypt implementation) |

# 5. Algorithms NOT used (and why)

| Algorithm | Why not |
|---|---|
| MD5 | Cryptographically broken; never used in security contexts |
| SHA-1 | Deprecated for signatures and HMAC by NIST SP 800-131A |
| DES / 3DES | NIST-deprecated |
| RC4 | NIST-deprecated |
| ECB-mode block ciphers | Pattern-preserving; never used |
| HS256 (HMAC-signed JWT) | Refused — see §2.3 |
| Plain HTTP for browser surface | Refused at customer reverse proxy |
| Custom crypto (roll-your-own) | Never — always use the language standard library or audited libraries |

# 7. Crypto-agility

ION's cryptographic operations are abstracted behind module boundaries so future algorithm migrations are tractable:

| Module | Current algorithm | Migration boundary |
|---|---|---|
| `auth/password.py` | bcrypt | Single function `hash_password()` + `verify_password()`; migrate to Argon2id without touching callers |
| `auth/oidc.py` | RS256 | Algorithm whitelist in one place; can be expanded to RS384/RS512/ES256 |
| `services/case_ledger_service.py` | SHA-256 | Ledger row has `algorithm` column (default `sha256`); SHA-3 would be a new value + parallel verifier |
| `services/webhook_service.py` | HMAC-SHA256 | Signature header version-prefixed (`sha256=`); future `sha3-256=` is forward-compatible |

# 8. FIPS 140-2/3 alignment

ION does not currently package a FIPS-validated cryptographic module. The libraries used (Python `hashlib`, `hmac`, `secrets`, `bcrypt`) rely on the underlying OpenSSL (in Python's standard library). On customer environments where the OS-level OpenSSL is FIPS-validated, ION's cryptographic operations inherit that validation.

If formal FIPS 140-2 or 140-3 mode is required, customer can run ION's container on a FIPS-validated host OS (RHEL FIPS mode, Ubuntu FIPS subscription) — no ION code change needed.

# 9. NCSC alignment

| NCSC guidance | ION's position |
|---|---|
| TLS 1.2 minimum (preferably 1.3) | Customer reverse proxy enforces |
| Hash: SHA-2 minimum (SHA-256+) | SHA-256 used; SHA-1 + MD5 not used |
| Symmetric: AES 128/256 in GCM/CCM | Application doesn't directly use symmetric ciphers; OpenSSL-via-library handles where needed |
| Asymmetric: RSA 2048 minimum, ECDSA P-256+, EdDSA Ed25519 | OIDC requires RSA 2048 minimum |
| Random: OS CSPRNG | Python `secrets` module used |

# 10. Cryptographic incident response

If an algorithm or implementation is compromised (e.g. a new break against SHA-256), the response procedure is:

| Step | Action |
|---|---|
| 1 | ION maintainer issues advisory + planned migration window |
| 2 | Ledger schema migration: add new ledger rows with the new algorithm; old chain remains verifiable until customer retires it |
| 3 | Per-customer rotation plan in `_mod_through_life_plan.md` cadence |
| 4 | Customer's `_mod_exception_register.md` carries the transition exception while in progress |

See `_mod_ion_incident_response.md` §5.5 for the operational procedure.

# 11. Cryptographic verification at deployment

The customer can verify ION's cryptographic stance at any time:

```bash
# Confirm image digest matches a known-good
docker inspect ixion36/ion:0.29.1 --format '{{.RepoDigests}}'

# Confirm SBOM is intact in the deployed image
docker run --rm ixion36/ion:0.29.1 cat /app/sbom.spdx.json | jq '.creationInfo'

# Confirm RS256-only at OIDC surface (attempted HS256 token should be refused)
curl -H "Authorization: Bearer <hs256-token>" https://ion.example/api/me
# Expected: 401 Unauthorized + "RS256 only" diagnostic
```
